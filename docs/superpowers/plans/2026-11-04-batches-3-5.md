## Batch 3 — Resources redesign
- A resource is ONE row, not a card with items. Fields: `title` (what it is), `value` (long text, ALWAYS encrypted at rest), labels, `created_by`, created date, viewers (who can view).
- `value` uses the same markdown editor as tasks (<x-ui.markdown-editor>) with image and PDF attachments (existing HasAttachments / Attachment model). Attachment file CONTENTS are encrypted at rest too; download/serve decrypts, only for the resource's viewers/editors (extend the attachment download authorisation; images inline only for png/jpeg/gif/webp, PDFs download, nosniff).
- List looks like the module list: lock icon, title, labels (label chips), added-by avatar, date, viewer avatars with the shared assignees component ("+" to add viewers), chevron. Clicking a row expands it; the value is NOT in the page until expanded: it is fetched from the server on expand (so the secret is not in page source and the access log is accurate) and rendered as markdown. Expanded view: Copy button, Edit pencil (edit permission only), delete in a menu, and an Access log for editors.
- Permissions: edit = creator, super admin, project manager; view = listed viewers (+ editors). Clients see only resources they are listed as a viewer on. Search box + label filter above the list. "+ Add resource" opens a pop-up form (title, value editor, labels, viewers).
- Labels: reuse labelables (HasLabels). Seed default labels Production, Staging, Development (super admin can add more; only super admin creates labels).
- Access log: reuse the activities table and the timeline component: events `viewed` (when a row is expanded and the value is revealed), plus edited, viewers changed, deleted. Never write the secret into the log. Dedupe repeated reveals by the same user within 5 minutes. Editors see "Access log" in the expanded row; a small note "Access to this value is logged" shows on the row. Existing resource_items structure is removed (demo data only).
- Tests: encryption at rest (raw DB value is not plaintext), no value in initial HTML, reveal logging + dedupe, permission matrix (viewer, non-viewer, client, editor), attachment encryption/serving, label filter/search, seeded labels, XSS-safe markdown.

## Batch 5 — task numbers, one budget amount per task, module cap, add-ons, sprint billing
> **Superseded in part (5c):** the budget model below was simplified. Money is the cap (module `billing_mode` fixed|hourly; hourly cap = hours × rate kept in `budget_amount`); tasks follow the module with an optional per-task override (`tasks.billing_mode`, `hourly_rate`, `billable_hours`); hourly task value = billed hours × rate, recomputed when time entries change; only manual FIXED edits are blocked, with ONE action (raise the module amount). Removed: rebalance, add-on create/accept (`addon_accepted_*`), the distribute helper, calculated project totals. Project Initial/Add-ons are typed again (Final = sum) with an informational "Allocated to modules" line. Task codes, sprints and the sprint invoice line are unchanged.

Decisions (user, original 5b):
- **Task number:** unique per project, never reused/changed; shown as `KEY-12` where KEY is a project key (3–5 letters, auto-derived from the project name, unique, editable on the project form). Tasks get `project_id` and `number` (assigned in a transaction from a per-project counter); copies get a new number; a converted subtask gets the next number; subtasks have no number. Show it on the task page title/breadcrumb, board cards and panel, Modules tab and sprint rows, timeline mentions, and make search find it (`NWS-12`).
- **One amount per task:** no separate price. Rename tasks.price → `budget_amount`, `local_price` → `budget_amount_local` (task value for every task; add-ons use the same field). Update the task form, billing, seeder, tests, FreezesLocalAmounts config.
- **Values are stored, never silently rewritten:** module `budget_amount` is the CAP. Module panel shows Budget, Allocated (Σ task values), Remaining, and Done value. Tasks start without a value. A "Distribute remaining budget by hours" helper (preview first, confirm to apply) fills only tasks without a value: remaining = budget − Σ priced; each unpriced task gets remaining × its hours ÷ Σ unpriced hours (rounded, last absorbs the remainder). Example: 100 with 2h, 2h, 4h → 25, 25, 50.
- **Block over-budget edits:** setting a task value that makes Σ task values exceed the module budget (or lowering the module budget below Σ task values) is blocked with a message and three explicit actions: raise the module budget (logged with a reason), create an add-on task, or rebalance the others (shows the exact resulting numbers, applies only on confirm). A new task when nothing remains starts with no value and a "remaining 0" notice with the same options.
- **Hourly clients:** value derived from hours × module hourly rate and the cap is the module's budget hours; same block/preview/options in hours.
- **Add-ons:** an out-of-scope task with an amount is an add-on. It starts as `proposed`; after the client confirms, a user with manage-money clicks "Accept add-on", which raises the module's budget by its amount (logged budget change with reason "Add-on: KEY-n") and counts in the project's add-ons.
- **Project budget fields become calculated:** Initial = Σ module base budgets, Add-ons = Σ accepted add-ons, Final = Initial + Add-ons = Σ module budgets. The project form's Initial/Add-ons inputs become read-only "from modules" (a new project starts at 0). Keep local-currency twins consistent.
- **Overruns:** a task going over its estimate does not change its value; overrun shows as logged hours vs estimate for manage-money users. Money amounts are visible only to users who can manage money.
- **Sprint billing:** a completed sprint's done value (Σ values of its Done tasks) is billed as ONE invoice line: "Sprint 3 (Nov 4 – Nov 18): completed KEY-12, KEY-15, KEY-21" with that value; its tasks are marked as billed (existing invoiced rule) so they cannot be billed twice. Done tasks outside any sprint still bill as their own lines with their numbers in the description. The sprint completion summary shows planned value, done value, carried-over value.
- Tests: number assignment (concurrency-safe, per project, never reused, copy/convert), key generation/uniqueness/edit, search by number, the cap/block/options/preview flows, distribute helper (incl. the 25/25/50 example and rounding), hourly mode, add-on accept flow and project totals, calculated project fields, sprint billing line content and no double billing, permissions (money visibility), rename migration consequences across billing/portal/tests.
